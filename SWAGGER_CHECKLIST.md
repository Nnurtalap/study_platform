# Проверка проекта через Swagger

Инструкция составлена по исходникам backend и frontend, миграциям и OpenAPI-схеме приложения на 07.09.2026. Импорт `main_app`, генерация OpenAPI и настройка ORM проверены локально. Запросы с записью в БД и полный запуск Docker в рамках подготовки документа не выполнялись. Успешные ответы ниже — критерии проверки, а не отчёт о пройденных тестах.

В текущем коде есть дефекты: полный сценарий на чистой БД без исправлений не проходит. На заблокированном шаге запишите результат и продолжайте только независимые проверки. Не подставляйте выдуманные ID для обхода ошибки.

## 1. Что проверяем

Backend — FastAPI, PostgreSQL, SQLAlchemy, Alembic и FastAPI Users. Пользователи имеют роли `student`, `teacher`, `admin`; отдельно существует флаг `is_superuser`. Авторизация использует Bearer-токены, хранящиеся в БД, со сроком жизни по умолчанию 3600 секунд.

Основная цепочка: регистрация → предмет → тема → задание → тест → включение задания в тест → назначение студенту или группе → ответ студента → чтение ответа.

Frontend содержит регистрацию и вход; главная страница пустая. Для проверки Swagger запуск frontend не требуется. RabbitMQ объявлен в Compose, но отправка ответа на ИИ-проверку пока обозначена `TODO`; обработчика оценивания в проекте нет. `kiro.py` — отдельный пример обращения к API, к маршрутам проверки ответов он не подключён.

## 2. Запуск

Из корня проекта в PowerShell:

```powershell
cd backend
```

Убедитесь, что существует `fastapi-application/.env`. Если файла нет, создайте его из шаблона, сохранив существующий файл при его наличии:

```powershell
if (-not (Test-Path fastapi-application/.env)) {
    Copy-Item fastapi-application/.env.template fastapi-application/.env
}
```

Проверьте настройки:

| Переменная | Назначение |
| --- | --- |
| `APP_CONFIG__DB__URL` | Адрес PostgreSQL. Compose задаёт собственное значение с хостом `pg:5432`. Для запуска Python на хосте используйте `localhost:5433` и реквизиты БД из Compose. |
| `APP_CONFIG__ACCESS_TOKEN__RESET_PASSWORD_TOKEN_SECRET` | Секрет токенов восстановления пароля. |
| `APP_CONFIG__ACCESS_TOKEN__VERIFICATION_TOKEN_SECRET` | Секрет подтверждения почты. |
| `DEFAULT_EMAIL`, `DEFAULT_PASSWORD` | Данные автоматически создаваемого суперпользователя. |

`create_superuser.py` читает `DEFAULT_*` через `os.getenv`: Docker получает их из `env_file`, а при запуске Python на хосте их нужно экспортировать в окружение процесса. Чтение `.env` объектом Settings само по себе не экспортирует эти переменные. Существующему суперпользователю пароль при старте не меняется.

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 web
docker compose exec web alembic current
```

Compose выполняет `alembic upgrade head` перед запуском приложения. Текущая конечная миграция — `8e3d23ce67c9`. Используйте тестовую БД: старые заполненные таблицы могут мешать миграциям, добавляющим обязательные столбцы без заполнения старых строк.

Откройте:

- Swagger: http://localhost:8080/docs
- OpenAPI: http://localhost:8080/openapi.json

Для локального запуска вместо контейнера `web`, при установленных зависимостях Poetry и работающей БД:

```powershell
poetry install
cd fastapi-application
poetry run alembic upgrade head
poetry run uvicorn main:main_app --host 127.0.0.1 --port 8000 --reload
```

В этом варианте Swagger расположен на http://localhost:8000/docs. В `requirements.txt` отсутствует используемый приложением `aiohttp`, поэтому установка только этого файла не эквивалентна установке зависимостей проекта через Poetry.

Если документация не открывается, сначала смотрите логи запуска и миграций. Ответ `404` на `/` не означает, что API не работает: маршрут главной страницы backend не объявлен.

## 3. Как выполнять запросы

Раскройте метод → **Try it out** → заполните path/query-параметры и JSON → **Execute**. Проверяйте фактические **Server response / Code / Response body**; раздел с примерами Responses сам по себе не подтверждает успешное выполнение.

Ниже короткие пути начинаются после `/api/v1`, кроме явно указанного полного пути чтения ответа. Числа `1` в примерах заменяйте реальными ID из ответов. Swagger не подставляет сохранённые значения автоматически.

Записывайте `student_id`, `teacher_id`, `subject_id`, `topic_id`, `task_id`, `test_id`, `group_id`, `assignment_id`, `submission_id`. Для повторного прогона меняйте email, название и slug предмета, например суффикс `01` на `02`.

## 4. Регистрация и авторизация

### 4.1. Создать студента

`POST /auth/register`, без авторизации:

```json
{
  "email": "swagger.student01@example.com",
  "password": "SwaggerDemo2026!",
  "role": "student"
}
```

Ожидается `201`, пользователь с `id`, указанными email и ролью, `is_active: true`, `is_superuser: false`, `is_verified: false`. Пароль и его хеш в ответе отсутствуют. Сохраните `student_id`.

### 4.2. Создать учителя

Повторите `POST /auth/register`:

```json
{
  "email": "swagger.teacher01@example.com",
  "password": "SwaggerDemo2026!",
  "role": "teacher"
}
```

Ожидается `201`, `role: "teacher"`. Текущая схема позволяет передавать роль при регистрации. Сохраните `teacher_id`. Для проверок изоляции аналогично создайте второго студента и второго учителя с суффиксом `02`.

### 4.3. Войти как учитель

`POST /auth/login` принимает **форму**, а не JSON:

| Поле | Значение |
| --- | --- |
| `username` | `swagger.teacher01@example.com` |
| `password` | `SwaggerDemo2026!` |
| `scope`, `client_id`, `client_secret` | Не заполнять |
| `grant_type` | `password`, если Swagger требует значение |

Ожидается `200`, `access_token` и `token_type: "bearer"`.

Нажмите **Authorize** вверху Swagger. В секции **HTTPBearer** вставьте только значение `access_token`, без префикса `Bearer`, затем **Authorize → Close**. Альтернатива — войти через секцию **OAuth2PasswordBearer**, используя email в поле username. Не оставляйте разные учётные записи одновременно в двух схемах авторизации.

Вызовите `GET /users/me`: ожидается `200`, email учителя и `role: "teacher"`. Убедитесь, что в сгенерированном curl есть `Authorization: Bearer ...`. Сам вызов `/auth/login` не гарантирует, что Swagger начнёт добавлять токен к следующим запросам.

Для смены роли очистите обе секции в **Authorize**, войдите нужным пользователем и снова проверьте `/users/me`. Подтверждение почты для входа сейчас не требуется.

## 5. Основной сценарий учителя

### 5.1. Предмет

`POST /subjects`:

```json
{"name": "Математика Swagger 01", "slug": "math-swagger-01"}
```

Ожидается `201` с `id`, `name`, `slug`. Сохраните `subject_id`. Повторный запрос должен дать `409` с `Subject with this name or slug already exists`.

`GET /subjects` должен вернуть `200` и массив предметов, отсортированных по имени; авторизация не обязательна. **Текущий блокер:** сервис возвращает `list[...]` вместо `list(...)`, что ломает результат.

### 5.2. Тема

`POST /subjects/{subject_id}/topics`, path `subject_id` — ID из предыдущего шага:

```json
{"topic": "Линейные уравнения"}
```

Критерий после исправления: `201` с `id`, `name`, `subject_id`. Сохраните `topic_id`.

**Сейчас шаг заблокирован:** сервис вызывает `get_subject_or_404` без `session`, затем обращается к `data.name`, хотя входная схема объявляет `topic`. Замена JSON на `{"name": "..."}` проблему не решает: текущая схема требует `topic` и вернёт `422`.

Нормального `GET /subjects/{subject_id}/topics` нет. В Swagger есть ошибочный `POST /subjects/{subject_service}/topics` с query `subject_id`; он конфликтует по форме URL с маршрутом создания темы и не является рабочим способом получить список. После исправления маршрута проверяйте массив тем своего предмета и `404` для отсутствующего предмета.

### 5.3. Задание

Выполняйте после получения существующего `topic_id`. `POST /tasks`:

```json
{
  "title": "Линейное уравнение Swagger 01",
  "body": "Решите уравнение: 2x + 4 = 10",
  "task_type": "open_answer",
  "difficulty": "easy",
  "topic_id": 1,
  "correct_answer": "x = 3"
}
```

Критерий: `201`. Допустимые типы: `single_choice`, `multiple_choice`, `open_answer`; сложности: `easy`, `medium`, `hard`. Отдельного поля с вариантами выбора в схеме нет.

**Текущие ограничения:** enum в моделях и миграциях несовместимы, поэтому запись может завершиться ошибкой PostgreSQL. Кроме того, ответ объявлен как `TaskCreate`, поэтому `id` в нём отсутствует. `GET /tasks?topic_id=...` должен позволять найти созданное задание, но сейчас обработчик перекрывает одноимённую сервисную функцию и вызывает себя с неверными аргументами. Полностью через Swagger надёжно продолжить цепочку на чистой БД здесь нельзя.

После исправлений получите `task_id` из ответа создания или списка. `GET /tasks/{task_id}` должен вернуть `200`, данные задания и правильный ответ; этот метод доступен учителю.

### 5.4. Тест

Можно проверить независимо от создания темы. `POST /tests`:

```json
{"title": "Проверочная Swagger 01", "description": "Одно линейное уравнение"}
```

Ожидается `201` с `id`, названием, описанием и `test_tasks: []`. Сохраните `test_id`. Передавайте строковое описание: вход допускает `null`, а схема ответа требует строку.

`GET /tests/{test_id}` под создавшим тест учителем: `200`. Под другим учителем: `404` с `Test not found`.

### 5.5. Добавить задание в тест

`POST /tests/{test_id}/tasks`:

```json
{"task_id": 1, "position": 1, "points": 10}
```

Критерий после исправления: `201` с этими полями; повторное добавление — `409` с `This task is already in the test`. **Сейчас блокер:** обработчик перекрывает сервис `add_task_to_test` и вызывает сам себя с неверными аргументами.

Повторно прочитайте тест: `test_tasks` должен содержать задание. Сейчас ORM-связь называется `tasks`, а схема читает `test_tasks`, поэтому ответ может показывать пустой список даже при наличии связи в БД.

### 5.6. Назначить тест студенту

`POST /tests/{test_id}/assignments`:

```json
{"student_id": 1, "group_id": null, "due_date": null}
```

Замените `student_id`. Критерий: `201`, `id`, `test_id`, нужный `student_id`, `group_id: null`, `due_date: null`, `status: "assigned"`. Сохраните `assignment_id`. **Блокер:** несовпадение enum статуса с миграцией.

Ровно одно из `student_id` и `group_id` должно быть задано. Для дедлайна используйте ISO 8601 с часовым поясом, например `2099-12-31T23:59:59Z`.

## 6. Отдельная ветка: группа

Под учителем:

1. `POST /groups` с `{"name":"Swagger группа 01"}`. Критерий после исправлений: `201`, ID и название группы. Сейчас перепутаны аргументы сервиса, а `GroupRead` требует несуществующее у группы поле `email`.
2. `POST /groups/{group_id}/enrollments` с `{"student_email":"swagger.student01@example.com"}`. Критерий: `201`, `{"detail":"Student enrolled"}`; повтор — `409`. Сейчас проверка владельца группы не делает `await session.execute(...)`.
3. `GET /groups/{group_id}`. Критерий: `200` с `id`, `name`, массивом `students`, содержащим ID и email студента. Сейчас дополнительно перепутан порядок аргументов вызова сервиса.
4. `POST /tests/{test_id}/assignments` с `{"student_id":null,"group_id":1,"due_date":null}`. Критерий: `201`, назначение группе.
5. Под включённым студентом проверить `/me/assignments`, под посторонним — отсутствие этого назначения.

## 7. Ответ студента

Войти студентом и проверить `GET /users/me`.

### 7.1. Список назначений

`GET /me/assignments`: критерий — `200` и массив личных назначений плюс назначения групп студента. Сейчас сервис возвращает `List[...]` вместо списка, что ломает выдачу.

У студента нет отдельного маршрута получения содержимого назначенного теста: `GET /tests/{test_id}` и чтение заданий требуют учительского доступа. В ручном сценарии используйте сохранённые ID; отсутствие студенческого чтения содержимого фиксируйте отдельно.

### 7.2. Отправить ответ

Фактический маршрут в текущей OpenAPI: `POST /api/v1/test-assignment/{assigment_id}/submissions`.

В пути опечатка `assigment_id`, а зависимость ожидает `assignment_id`. Поэтому Swagger показывает обязательный **query-параметр** `assignment_id`, а path-параметр не описан. Это дефект контракта; ID проверяется именно из query. После исправления имя должно совпадать в маршруте и зависимости. До исправления не считайте такую проверку подтверждением корректной привязки к ID в URL.

Тело запроса:

```json
{"task_id": 1, "answer_text": "2x = 6, поэтому x = 3"}
```

Критерий: `201`, `id`, правильные `task_id` и `test_assignment_id`, отправленный текст, `status: "pending"`, `analys: null`. Сохраните `submission_id`. Первое отправленное решение переводит назначение из `assigned` в `in_progress`.

Возможен дополнительный сбой сериализации: после создания ответа связь `analys` явно не загружается, хотя читается схемой ответа; при асинхронной ленивой загрузке возможен `MissingGreenlet`. После `500` не делайте вывод, что запись отсутствует: commit выполняется до формирования ответа, повтор может дать `409`.

### 7.3. Прочитать ответ

Фактический полный путь: `GET /api/v1submission/{submission_id}` — **без `/` между `v1` и `submission`**. Такой путь подтверждён генерацией OpenAPI. Выберите именно его в Swagger; `/api/v1/submission/...` сейчас не зарегистрирован.

Ожидается `200` для владельца и `404` с `Submission not found` для другого студента. У этого чтения связь `analys` загружается явно.

Автоматического перехода в `graded`, заполнения анализа, завершения теста или фонового перевода в `overdue` сейчас нет. Не ждите оценки после обновления страницы. Для первой реализации критерий — сохранённый ответ со статусом `pending`.

## 8. Дополнительные проверки Auth и Users

| Проверка | Действия | Критерий |
| --- | --- | --- |
| Профиль | `GET /users/me` с токеном | `200`, текущий пользователь |
| Изменение профиля | `PATCH /users/me`, `{"email":"swagger.student01.updated@example.com"}` на отдельном тестовом пользователе | `200`, email изменён; затем восстановить email или использовать новый при входе |
| Восстановление пароля | `POST /auth/forgot-password`, `{"email":"swagger.student01@example.com"}` | `202`; токен выводится в логи backend, почтового отправителя нет |
| Новый пароль | `POST /auth/reset-password`, `{"token":"ТОКЕН_ИЗ_ЛОГА","password":"SwaggerNew2026!"}` | `200`; новый пароль позволяет войти, старый даёт `400` |
| Запрос подтверждения | `POST /users/request-verify-token`, `{"email":"swagger.student01@example.com"}` | `202`; токен из логов |
| Подтверждение | `POST /users/verify`, `{"token":"ТОКЕН_ИЗ_ЛОГА"}` | `200`; `/users/me` показывает `is_verified: true` |
| Чтение пользователя | `GET /users/{id}` под суперпользователем | `200`; обычный пользователь получает `403` |
| Изменение пользователя | `PATCH /users/{id}`, `{"role":"teacher"}` под суперпользователем на отдельной учётной записи | `200`, роль обновлена |
| Удаление пользователя | `DELETE /users/{id}` под суперпользователем, только отдельная одноразовая учётная запись без данных сценария | `204`; последующее чтение — `404` |
| Выход | `POST /auth/logout` с текущим токеном | Проверить фактический успешный ответ и затем `401` на `/users/me` с тем же токеном; OpenAPI декларирует `200` |

Для токенов восстановления/подтверждения смотрите `docker compose logs --tail 100 web` из `backend`. `202` для запроса восстановления не доказывает существование email. Действие **Logout** в окне Swagger только убирает локальную авторизацию; для отзыва токена используйте API logout.

`role: "admin"` не равен `is_superuser: true`: административные методы FastAPI Users требуют именно суперпользователя. Учительский и студенческий доступ допускает суперпользователя, поэтому основные проверки ролей проводите обычными учётными записями.

Webhook `user-created` в Swagger описывает исходящее событие, а не входной API-метод. После регистрации приложение отправляет уведомление на `https://httpbin.org/post`; реальной отправки письма с подтверждением нет. Используйте вымышленные тестовые email, как в примерах.

## 9. Негативные проверки

Проверки зависимых сущностей выполняйте после исправления соответствующих блокеров и создания исходных данных. `500` фиксируйте как дефект, а не как успешное отклонение запроса.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Повторная регистрация того же email | `400`, `REGISTER_USER_ALREADY_EXISTS` |
| Некорректный email или `role: "owner"` при регистрации | `422` |
| Неверный пароль при входе | `400`, `LOGIN_BAD_CREDENTIALS` |
| `/users/me` без токена или с выдуманным токеном | `401` |
| Студент создаёт предмет, группу, задание или тест | `403`, `Это действие доступно только учителям` |
| Учитель вызывает `/me/assignments` | `403`, `Это действие доступно только студентам` |
| Несуществующая тема при создании задания | `400`, `Topic does not exist` |
| Недопустимые `task_type` или `difficulty` | `422` |
| Чужой или отсутствующий тест при чтении/изменении | `404`, `Test not found` |
| Повторное включение задания в тест | `409`, `This task is already in the test` |
| Оба адресата назначения заданы или оба отсутствуют | `422`, `Specify exactly one of student_id or group_id` |
| Несуществующий студент при назначении | `400`, `Student does not exist` |
| Несуществующая группа при назначении | `400`, `Group does not exist or is not yours` |
| Зачисление email, которого нет в БД | `404`, `User with this email not found` |
| Зачисление учителя в группу | `400`, `This user is not a student` |
| Повторное зачисление студента | `409`, `Student is already enrolled in this group` |
| Ответ на чужое/несуществующее назначение | `404`, `Assignment not found` |
| Ответ после дедлайна: создать отдельное назначение с `due_date: "2000-01-01T00:00:00Z"` | `400`, `Assignment deadline has passed` |
| Ответ на задание, не включённое в назначенный тест | `400`, `This task is not part of the assigned test` |
| Повторный ответ того же студента на то же задание в том же назначении | `409`, `You have already submitted an answer for this task` |
| Другой студент читает сохранённый ответ | `404`, `Submission not found` |
| Некорректный токен сброса/подтверждения | `400` |

Отдельные проверки недостаточной валидации: самоповышение роли через `PATCH /users/me`, выбор привилегированной роли при регистрации, назначение теста пользователю-учителю, назначение чужой группе, отрицательные `points`/`position`, пустой `answer_text`. В коде соответствующие ограничения отсутствуют или неполны; не ожидайте автоматически `403`/`422`. Зафиксируйте фактическое поведение для согласования правил доступа и валидации. Изменение роли проводите на отдельной учётной записи.

Проверку `Assignment already completed` нельзя подготовить только через текущий Swagger: маршрута завершения назначения нет. Также последовательный повтор ответа не проверяет защиту от одновременных дублей — уникального ограничения на `(student_id, test_assignment_id, task_id)` в модели и миграциях нет.

## 10. Найденные причины блокировок

Все пути ниже относительно `backend/fastapi-application`.

| Файл | Дефект и влияние |
| --- | --- |
| `core/services/subject_service.py` | `list[...]` вместо списка; пропущен `session` в вызове поиска предмета; `data.name` не соответствует `TopicCreate.topic`. |
| `api/api_v1/endpoints/subjects.py` | Список тем объявлен как POST с `{subject_service}` вместо GET с согласованным `{subject_id}`; конфликтует с созданием темы. |
| `api/api_v1/endpoints/group.py`, `core/services/group_service.py` | Перепутан порядок аргументов создания и чтения; отсутствует `await` при поиске группы. |
| `core/schemas/group.py` | `GroupRead` требует `email`, которого у группы нет. |
| `api/api_v1/endpoints/tasks.py` | `list_tasks` перекрывает импорт сервиса; создание использует схему ответа без `id`. |
| `api/api_v1/endpoints/tests.py` | `add_task_to_test` перекрывает одноимённый сервис. |
| `core/schemas/test.py`, `core/models/test.py` | `test_tasks` в схеме против `tasks` в ORM; `description` не допускает `null` в ответе, хотя допускает во входе и БД. |
| `core/models/task.py`, `core/models/test_assignment.py`, миграция `6f8cdd1376dc` | SQLAlchemy Enum по умолчанию хранит имена элементов (`OPEN_ANSWER`, `EASY`, `ASSIGNED`), а миграция создала строчные значения (`open_answer`, `easy`, `assigned`). Нужно согласовать модели и БД; менять регистр JSON бесполезно. |
| `core/services/test_assignment.py` | `List[...]` вместо списка; при назначении не проверяется роль адресата и принадлежность группы учителю. Неиспользуемая функция проверки доступности также содержит неверные сравнения и пропущенный вызов метода. |
| `api/api_v1/endpoints/submissions.py`, `api/api_v1/dependencies/assignments.py` | `assigment_id` в URL против `assignment_id` в зависимости; чтение ответа зарегистрировано по `/api/v1submission/...`. |
| `core/services/submission_service.py` | При создании связь анализа явно не загружается для сериализации; нет ограничения БД против конкурентных дублей. |

## 11. Шаблон отчёта

Для каждого шага заполняйте:

| Шаг | Пользователь/роль | Метод и URL | Входные ID/JSON | Ожидается | Фактический код и тело | Итог |
| --- | --- | --- | --- | --- | --- | --- |
| 5.1 | teacher01 / teacher | POST /api/v1/subjects | name, slug | 201 | Заполнить | PASS / FAIL / BLOCKED |

`PASS` — совпали код, содержимое и права доступа. `FAIL` — запрос выполнен, результат неверен. `BLOCKED` — нет необходимых данных из-за предыдущей ошибки. Для `500` приложите traceback из логов без паролей и токенов.

Полный сценарий пройден, когда учитель создал тест с заданием, назначил его, нужный студент отправил и прочитал свой ответ, повтор отклонён, а другой студент не получил доступ. Отсутствие ИИ-оценки отражайте как нереализованную функцию, а не как зависшую проверку.
