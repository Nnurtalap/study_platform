# Проверки email-аутентификации backend

## Запуск

Из папки `backend`, при запущенных сервисах `pg` и `web`:

```powershell
docker compose exec -T web python run_email_auth_checks.py
```

В конце успешного прогона:

```text
ALL EMAIL AUTH BACKEND CHECKS PASSED
Removed isolated check database
```

Роль PostgreSQL, заданная в конфигурации приложения, должна иметь право
`CREATEDB`. Локальный Compose использует роль с таким правом. Запускайте
проверки в окружении разработки.

## Как устроен прогон

`fastapi-application/run_email_auth_checks.py` создаёт БД со случайным именем
`email_auth_check_<uuid>` на настроенном сервере PostgreSQL. Адрес этой БД
передаётся только дочерним тестовым процессам. Рабочие API, Beat и воркеры
продолжают использовать свою БД.

1. Применяет всю цепочку миграций к пустой БД.
2. Повторяет `alembic upgrade head`, проверяя повторный запуск.
3. Запускает существующие `check_dispatch.py`, `check_delivery.py`,
   `check_code_issue.py`, `check_change_password.py`, `check_email_change.py`.
4. Запускает `test_email_auth_backend.py` через `unittest`.
5. Удаляет созданную БД в `finally`, в том числе при падении проверки.

Новый набор тестов проверяет имя подключённой БД перед очисткой своих данных.
Не запускайте отдельные старые `check_*.py` вместо общего запуска: сами по
себе они используют БД приложения, а диспетчер может конкурировать с Beat.

## Что проверяется

- Регистрация через HTTP, параллельная выдача и подтверждение кода.
- Неверный, просроченный, исчерпавший попытки и повторно использованный код.
- Повторная выдача кода и отмена письма предыдущего поколения.
- Сброс пароля с отзывом всех токенов и одинаковым ответом для неизвестного email.
- Смена пароля и email через защищённые HTTP-маршруты.
- Смена старого короткого пароля на пароль по новой политике.
- Запрет изменения email, пароля и привилегий через обычное обновление профиля.
- Запрет входа неподтверждённому пользователю и использования его токена.
- Лимиты при конкурентных запросах, HTTP 429 и `Retry-After`.
- Скрытие входных значений в ошибках валидации, `Cache-Control: no-store`,
  ограничение размера тела, включая поток без `Content-Length`.
- Откат регистрации и потребления кода при ошибке добавления уведомления.
- Повторная публикация зависшего outbox, откат при ошибке брокера,
  конкурентная обработка одного письма, SMTP-повторы и предел попыток.
- Очистка просроченных зашифрованных писем, счётчиков и старых записей.
- Удаление пользователя с проверкой именно `AssignmentStudent.student_id`.

## Границы проверки

PostgreSQL, миграции, транзакции и хеширование паролей настоящие. HTTP-запросы
в новом наборе проходят через приложение FastAPI в процессе теста (ASGI),
включая маршруты, зависимости и middleware; сетевой порт Gunicorn не используется.

SMTP и публикация в RabbitMQ подменяются в тестовом процессе. Сбои этих
сервисов имитируются, настоящие письма не отправляются. Это проверяет логику
повторов, но не соединение с внешним SMTP и не перезапуск реального брокера.
Проверка скомпрометированных паролей отдельно тестируется с имитацией ответа
и недоступности сервиса; остальные сценарии выполняются без внешнего HTTP.

Успешно обработанная запись outbox защищена от обычной повторной обработки.
Остаётся окно сбоя: SMTP мог принять письмо, а процесс упал до фиксации `sent`
в PostgreSQL. В таком случае возможна повторная отправка. Гарантии «ровно одно
письмо при любом сбое» этот механизм не даёт.
